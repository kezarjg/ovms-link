# ABRP 3.0.0 — Scope & Decomposition Design

**Date:** 2026-06-02
**Author:** kezarjg (with Claude Code)
**Status:** Approved for decomposition (epic-level scope; each sub-project gets its own spec → plan cycle)
**Branch:** `feature/abrp-3.0.0`

This is an **epic-level** scope/decomposition spec, not a single implementation
spec. 3.0.0 spans delivery, onboarding, observability, and new vehicle-facing
behavior. It is decomposed into three sub-projects; each gets its own
brainstorm → spec → plan → implement cycle and ships as a `3.0.0-alpha/beta`
milestone. See `ROADMAP.md` for how 3.0.0 sits after 2.3.x / 2.4.0.

## 1. Goal

Transform ovms-link from a hand-copied single-file script into an **installable,
self-updating OVMS plugin** with friendly onboarding, live visibility, and
plan-awareness — "the full platform leap."

## 2. Scope

**In scope (3.0.0):**

- **Delivery:** package as an OVMS plugin (manifest + repository →
  `plugin install` / `plugin update`); **retire the manual hand-copy** path
  (plugin-only).
- **Structure:** split the single `abrp.js` into focused modules under
  `plugin/abrp/*` (see §5).
- **Cert handling:** **proactively** install the bundled non-embedded roots
  (GoDaddy G2 + GlobalSign R1) + `tls trust reload` at first run, idempotently, so
  CloudFront's chain-rotation can't cause the recurring "SSL Error"; a reactive
  re-install is an optional fallback (see §6).
- **Onboarding & UI:** a web **config page** (paste-token, replaces the
  `config set` shell command); a **status/plan dashboard**; a **status hook** into
  the OVMS status page.
- **Plan awareness (read-only):** `get_next_charge` / `get_latest_plan` →
  **driver notifications** and dashboard display.

**Deferred (post-3.0):**

- **OAuth2** token onboarding (config-page paste-token ships first; OAuth2 needs an
  embedded-friendly redirect strategy).
- **Auto-limit / stop charging** (vehicle control). 3.0 is notify-only — no control.
- **Dual/manual delivery** — 3.0 is plugin-only.

**Non-goals:** the paid ABRP **Planning API** (route generation); `set_next_charge`
(writing the goal from OVMS); multi-vehicle support.

## 3. Constraints (carried from the current system)

- **Duktape / ES2015** — `var` + `function` only; no arrow functions, template
  literals, or object spread in the deliverable. (Tests run under Jest and may use
  modern JS.)
- **Host globals injected** — `HTTP`, `OvmsConfig`, `OvmsMetrics`, `OvmsNotify`,
  `PubSub`, `performance`, `print`, plus (new for 3.0) `VFS` and `OvmsCommand`
  (both confirmed available to Duktape scripts and used by cert handling).
- **Plugin delivery** — files install to `/store/plugins/abrp/`; a `module` element
  is auto-loaded via `require("plugin/abrp/<path>")`; a plugin install **leaves
  `ovmsmain.js` untouched** (verified), so the plugin ships **no `ovmsmain.js`**.
  Module require ids therefore use the `plugin/abrp/*` prefix.

## 4. Decomposition into sub-projects

```
  SP1 — Packaging foundation + cert handling      3.0.0-alpha.1   (must be first)
        │  everything depends on it
        ├──────────────┐
        ▼              ▼
  SP2 — Plan API    SP3 — Web UI                       beta
        + notifs ───▶ (config + dashboard + hook)
   3.0.0-alpha.2        3.0.0-beta.1
```

### SP1 — Packaging foundation + cert handling *(first; foundation)*

- Plugin **manifest** (`name`/`version`/`prerequisites`/`elements`) +
  **distribution** (independent Iternio repo and/or `openvehicles` default repo —
  decided in SP1's brainstorm); `plugin install` / `plugin update`; retire manual
  hand-copy.
- **Module split** (§5), including the Jest `moduleNameMapper` strategy for the
  `plugin/abrp/*` ids.
- **Cert handling** — proactive curated-root install + reactive fallback (§6).
- *Purpose:* install once, painless updates, TLS "just works." No new telemetry
  features — pure delivery + robustness, cleanly testable.

### SP2 — Plan-awareness API + notifications *(depends on SP1)*

- `planning.js` wrapping `get_next_charge` / `get_latest_plan` (reuses the existing
  token), sparingly polled (e.g. `get_next_charge` only while charging, every few
  minutes); **driver notifications** (next charge target, plan summary). Read-only.
- *Purpose:* turn ABRP's plan into driver-visible info; produces the data SP3 shows.

### SP3 — Web UI *(depends on SP1 for elements, SP2 for data)*

- **Config page** (paste token), **status/plan dashboard** (sending state, queue
  depth, last result, current telemetry, plan from SP2), **status hook**.
- *Purpose:* friendly setup + live visibility.

**Sequencing:** SP1 → then SP2 and SP3 (parallelizable; SP2 first so SP3 has real
data to render). Each milestone is independently shippable and testable.

## 5. Module decomposition of `abrp.js`

Today everything is one file (~870 lines). Split into focused modules
(`lib/abrp/*.js` in the repo → `plugin/abrp/*` installed). Dependency graph is a
DAG (no cycles); `util`, `metrics`, `config` are near-pure and trivially testable.

| Module | Responsibility | Key contents | Depends on | Milestone |
| --- | --- | --- | --- | --- |
| `util.js` | Pure helpers + logging | `logger`, `timestamp`, `clone`, `round`, `medianPowerMetrics` | — (`print`) | SP1 |
| `config.js` | Token + config | token state, `validateUsrAbrpConfig`, reset | `OvmsConfig`, `OvmsNotify` | SP1 |
| `metrics.js` | Metric definition + resolution | `metricMap`, `overrideMetricMap`, `isOvmsMetricSupported`, `getOVMSMetric`, `createTelemetry` | `util`, `OvmsMetrics`, `performance` | SP1 |
| `queue.js` | Queue + cadence + smoothing | queue/collected/lastQueued state, `queueTelemetry*`, `removeTelemetry`/`removeTelemetryBatch`, `isSignificantTelemetryChange`, `calculateMaxElapsedDuration` | `util`, `metrics` | SP1 |
| `iternio.js` | Shared transport | URL/key/token builder, `HTTP.Request` wrapper, `isApiOk`, optional reactive cert-heal hook | `config`, `certs`, `HTTP` | SP1 |
| `telemetry.js` | Telemetry **write** path | `sendTelemetry`, `createBulkPost`, `sendBulkTelemetry`, `isSending` | `iternio`, `queue` | SP1 |
| `certs.js` | Bundled non-embedded roots + proactive install | GoDaddy G2 + GlobalSign R1 PEMs, `ensureInstalled()` (idempotent) (+ optional reactive heal) | `VFS`, `OvmsCommand` | SP1 |
| `events.js` | Lifecycle / wiring | `subscribe`/`unsubscribe` + subscriptions state, vehicle callbacks, `manageVehicleStateEvents`, `checkTime`, `send` start/stop, `isActive`/`isTimeValid` | `queue`, `telemetry`, `config`, `PubSub`, `OvmsMetrics` | SP1 |
| `planning.js` | Planning **read** path | `getNextCharge`, `getLatestPlan` | `iternio` | **SP2** |
| `abrp.js` *(entry)* | Public commands + init | `info`, `onetime`, `send`, `resetConfig`, startup wiring, exports | all | SP1 |

**Telemetry vs planning split (decided):** the Iternio client is split into a
shared `iternio.js` transport + a `telemetry.js` write path + a `planning.js` read
path. Rationale: telemetry is a high-frequency, queue-coupled push; planning is a
sparse, UI-coupled pull; they live in different milestones. The shared plumbing
(URL/auth, `isApiOk`) is factored into `iternio.js` so it is not
duplicated. SP1 ships `iternio.js` + `telemetry.js`; SP2 adds `planning.js` without
touching the telemetry path.

**Shared-state strategy:** each module **owns its mutable state and exposes accessor
functions** (extending the existing `__test` seam pattern, e.g. `queue.snapshot()`,
`queue.removeBatch()`, `config.token()`). No god-`state.js`. This keeps modules
independently testable and avoids cross-module file-level coupling.

## 6. Cert handling architecture (SP1)

`api.iternio.com` is behind Amazon CloudFront, which **rotates the served cert
chain** over time (verified live: roots at Amazon Root CA 1, embedded in firmware;
historically GoDaddy-rooted). OVMS embeds ~7 roots; cert breakage (#39, #35) is
intermittent because it depends on which root the current chain uses. The plugin
**cannot inspect the presented chain from JS**, so it can't identify a missing root
at runtime — the determination is done **at build time** (inspect the chain with
`openssl`) and the **needed non-embedded roots are pinned in-source**.

The two `trustedca/` roots **not** in firmware are **GoDaddy Root G2** and
**GlobalSign Root R1** — these are what `certs.js` bundles (ISRG X1 and Amazon's
root are already embedded; `amazon.pem` is an intermediate).

- **Primary — proactive, idempotent install at startup:** `certs.ensureInstalled()`
  writes any missing bundled root to `/store/trustedca/abrp-<name>.crt` and runs
  `OvmsCommand.Exec("tls trust reload")` **once**, only when a cert is absent. No
  TLS-error detection, no guessing which root, no false-positive risk; normal boots
  touch nothing.
- **Fallback — reactive (optional):** if a send still fails on TLS (a future root
  outside the curated set), re-run `ensureInstalled()` once per session; the
  at-least-once queue retries on the next `ticker.10`. May be deferred if the
  proactive install proves sufficient.

**Safety:** certs are **bundled/pinned** in the plugin, **never fetched over the
network** (fixing trust via an untrusted connection would be chicken-and-egg). The
install only **adds** the curated roots; it never removes/alters existing trust.

## 7. Open decisions deferred to each sub-project's brainstorm

- **SP1:** distribution route (independent Iternio repo vs `openvehicles` default
  repo, or both); exact bundled-cert set (which non-embedded CAs); Jest
  `moduleNameMapper` mechanics; whether to also verify with `tls trust list`;
  whether cadence splits out of `queue.js`.
- **SP2:** poll cadence/limits; notification content/format; exact response shapes
  (need a real token or the Postman doc to pin down).
- **SP3:** dashboard framework (Highcharts à la `pwrmon`, or plain HTML); config
  page auth level; how the status hook renders.

## 8. Risks

- **Migration:** plugin-only retires manual install; existing users must migrate to
  `plugin install`. Mitigate with clear release notes and (since `openvehicles`
  already redirects to this project) a smooth default-repo path.
- **Cert detection precision:** a network error misread as a cert error costs one
  harmless cert write + reload per session — low cost; the once-per-session guard
  bounds it.
- **Jest resolution of `plugin/abrp/*` ids** must be solved early in SP1 or the
  whole suite can't import the split modules.
- **3.0 is large:** strictly milestone-gated delivery (alpha/beta) keeps each piece
  reviewable and testable; do not attempt all three sub-projects on one branch.
- **Ticker-handler latency (be mindful when adding per-cycle work).** The plugin runs
  entirely on the shared Duktape event thread (`ticker.1` collect, `ticker.10` bulk
  send). Field logs from 2026-06-04 (driving a Toyota e-TNGA) show this thread is
  already latency-sensitive on two fronts:
  - **I/O contention (common):** while driving with the web console streaming, the
    cellular UART and websocket job queues overflow and starve Duktape — `ticker.1`
    handlers ran 1–3.5 s and one `ticker.10` **bulk send blocked 8.1 s** while the
    modem was saturated. The plugin wasn't doing more work; it was waiting on the
    congested cellular link.
  - **Collection cost (rare but real):** once, `createTelemetry()`'s own
    synchronous sweep of the whole `metricMap` took **4074 ms** (it warns past 500 ms,
    `abrp.js:385`). This is O(metricMap size) of blocking `OvmsMetrics` reads and
    grows every time a telemetry key is added.

  Implication for SP2 (plan-awareness adds `get_next_charge`/`get_latest_plan` HTTP
  calls + OAuth2): **any new network call must be async/callback-driven like the
  existing bulk send — never synchronous on a ticker** — and new per-cycle metric
  work should be kept off the hot `ticker.1` path or batched, or it compounds both
  failure modes on an already-saturated link. (One-off 18 s stall the same day was an
  OTA firmware flash + reboot, not the plugin — excluded.)
