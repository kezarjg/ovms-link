# ABRP 3.0 — WS2: Plugin Packaging + gh-pages Distribution — Design

**Date:** 2026-06-05
**Status:** Approved design, pending implementation plan.
**Branch:** `feature/abrp-3.0.0`
**Parent:** `docs/superpowers/specs/2026-06-02-abrp-3.0.0-sp1-design.md` (SP1 WS2 section).
**Depends on:** WS1 (module split + `build.js` → `dist/abrp.js`) — shipped.

## 1. Summary

Package the bundled `dist/abrp.js` as an installable OVMS **plugin**: generate a
plugin manifest + repository index, publish them via **GitHub Pages** on a `gh-pages`
branch, and document the `plugin install abrp` flow. No behavior change — pure
delivery. The hand-copy install is kept as a documented fallback; the runtime CA-cert
step stays a manual prerequisite (WS3 automates it later).

## 2. Goals & non-goals

**Goals**
- `plugin repo install abrp <pages-url>` → `plugin install abrp` installs and runs the
  bundled plugin on a real OVMS module; `plugin update` upgrades it.
- The manifest version is derived from `constants.VERSION` (single source of truth).
- A repeatable `npm run release` publishes the Pages repo (no CI).

**Non-goals**
- No telemetry/behavior change.
- No web UI elements (SP3), no OAuth2, no cert automation (WS3).
- Not submitting to the `openvehicles` default repo yet (future; §9).
- Not retiring the hand-copy path (kept as a fallback).

## 3. Verified OVMS facts (the design rests on these)

- **Manifest schema** (from the live default repo, `api.openvehicles.com/plugins`): a
  plugin object has `name`, `title`, `version`, `maintainer`, `description`, `group`,
  `prerequisites` (array), `info` (URL), and `elements` (array). A `module` element is
  `{ "type":"module", "path":"<file>.js", "name":"<global>" }`.
- **Repo index** `plugins.json` is a JSON **array** of those plugin objects.
- **Element-file URL** resolves to `<base>/<name>/<path>` (verified:
  `api.openvehicles.com/plugins/chgind/chgind.js` is the real file).
- **Auto-load:** at each JS-engine start OVMS evaluates `abrp = require("plugin/abrp/abrp")`
  for the enabled `module` element (installed at `/store/plugins/abrp/abrp.js`),
  independently of `ovmsmain.js` — so the plugin ships **no `ovmsmain.js`**.
- **Single bundle ⇒ one module element.** Because `dist/abrp.js` is self-contained (its
  internal `__require` registry resolves all modules at build time), the plugin ships
  exactly one module file; the old multi-file `plugin/abrp/...` require-prefix problem
  does not arise.
- **Install TLS is free.** GitHub Pages chains to **ISRG Root X1**, embedded in OVMS
  firmware, so `plugin install` from Pages is trusted with no cert setup. (The plugin's
  own runtime TLS to `api.iternio.com` is a separate concern — WS3.)

## 4. Manifest

Generated by a pure function `buildManifest(version)` (in `publish.js`, Node-side —
NOT a Duktape module), reading `version` from `require('./lib/abrp/constants').VERSION`:

```json
[
  {
    "name": "abrp",
    "title": "A Better Routeplanner (ABRP) Live Telemetry",
    "version": "3.0.0-alpha.1",
    "maintainer": "Jerry Kezar <kezarjg@gmail.com>",
    "info": "https://github.com/kezarjg/ovms-link",
    "group": "Electric Vehicles",
    "description": "Streams live EV telemetry to ABRP via the Iternio Telemetry API.",
    "prerequisites": ["ovms>=3.3.004"],
    "elements": [{ "type": "module", "path": "abrp.js", "name": "abrp" }]
  }
]
```

`buildManifest` returns the array (one entry); `version` is interpolated from
`constants.VERSION`. The `name:"abrp"` module element preserves the global `abrp`, so
`script eval abrp.info()` keeps working.

## 5. Components & publish mechanism

**`publish.js`** (Node, dependency-free, repo root — sibling of `build.js`). Two pure,
testable functions plus an imperative CLI shell:

- `buildManifest(version)` → the plugins.json array (§4). Pure.
- `assemblePages(outDir, bundlePath, version)` → writes `outDir/plugins.json`
  (`JSON.stringify(buildManifest(version))`) and copies `bundlePath` →
  `outDir/abrp/abrp.js`; returns the written paths. Pure-ish (fs only, no git).
- **CLI (`npm run release`)**: `node build.js …` (build `dist/abrp.js`) → `assemblePages`
  into a staging dir → publish that tree to the **`gh-pages`** branch via a temporary
  `git worktree` (add worktree on `gh-pages`, replace its contents with the staging
  tree, commit, push), so the source working tree is never disturbed and built
  artifacts live only on `gh-pages`.

**gh-pages branch / Pages site** (served at `https://kezarjg.github.io/ovms-link/`):
```
plugins.json     # the array from buildManifest
abrp/abrp.js     # the bundled dist/abrp.js
```
**One-time manual setup (user, GitHub UI):** repo Settings → Pages → deploy from
`gh-pages` branch (root). Documented in the spec/README; not scriptable in-repo.

## 6. Install flow & README

README "Installation" gains a **primary** plugin path and keeps the existing build-it-
yourself flow as a **fallback**:

- **Install via OVMS plugin (recommended):**
  ```
  plugin repo install abrp https://kezarjg.github.io/ovms-link/
  plugin install abrp
  ```
  then reload the JS engine (`ABRP::started`). `plugin update` upgrades later. No
  `ovmsmain.js` step (auto-loaded).
- **Manual install (fallback):** the existing `npm run build` → copy `dist/abrp.js` to
  `/store/scripts/lib/abrp.js` + `ovmsmain.js` flow, retained for users who can't/won't
  use the repo.
- **CA certificates (still required for both methods):** the `trustedca/` install +
  `tls trust reload` step stays a documented manual prerequisite — the plugin's TLS to
  `api.iternio.com` needs it until WS3 automates it. (Plugin *install* from Pages is
  fine without it.)
- Token config (`config set usr abrp.user_token`) unchanged (config-page UI is SP3).

## 7. Testing

- **`buildManifest(version)`** (`node:test`): returns a one-entry array; the entry has
  `name === 'abrp'`, `version === <passed>`, `prerequisites` includes `ovms>=3.3.004`,
  and exactly one `module` element `{type:'module', path:'abrp.js', name:'abrp'}`.
- **Version wiring:** `buildManifest(require('./lib/abrp/constants').VERSION)` yields an
  entry whose `version` equals `constants.VERSION` (proves the single-source-of-truth).
- **`assemblePages`**: into a temp dir, assert `plugins.json` exists and
  `JSON.parse` round-trips to the expected array, and `abrp/abrp.js` exists with the
  bundle's bytes (copy fidelity).
- Wire `test/publish.test.js` into the `npm test` file list.
- **On-vehicle acceptance (manual, cannot be unit-tested):** `plugin repo install` +
  `plugin install abrp` on a real module; `script eval abrp.info()` shows the version;
  `plugin update` upgrades after a re-release.

## 8. Edge cases & risks

- **Enabling Pages is a manual GitHub-UI step** and the branch must exist before the
  first publish — `npm run release` creates/pushes `gh-pages`; the user enables Pages
  once. Documented.
- **`gh-pages` worktree hygiene:** the publish script must add/remove the temp worktree
  cleanly and never leave the main working tree on `gh-pages`. The plan pins exact
  `git worktree` commands and an always-remove cleanup.
- **Stale-version risk:** since the manifest version comes from `constants.VERSION`, a
  release without bumping `VERSION` republishes the same version. Acceptable for an
  alpha; the release doc says "bump `VERSION` first."
- **Element-path convention** is verified against the live repo (`<base>/<name>/<path>`),
  removing the main "will install even find the file" risk.

## 9. Out of scope / future

- **openvehicles default-repo submission** — a later path so users get `plugin install
  abrp` with **no** repo URL. First as a manual PR to the openvehicles plugin index
  (needs investigating their repo/source structure); a release-time automated PR is a
  possible enhancement after that. Tracked, not built here.
- **WS3 cert bootstrap** — proactive curated-root install so the runtime cert step is no
  longer manual.
