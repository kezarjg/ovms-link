# ABRP 3.0.0 — SP1: Packaging foundation + cert handling — Design

**Date:** 2026-06-02
**Author:** kezarjg (with Claude Code)
**Status:** Approved for planning
**Branch:** `feature/abrp-3.0.0`
**Parent:** `docs/superpowers/specs/2026-06-02-abrp-3.0.0-scope-design.md` (3.0.0 scope)

SP1 is the **delivery + structure + cert-robustness foundation** for 3.0.0.
Everything else (SP2 plan API, SP3 web UI) depends on it. It ships as
`3.0.0-alpha.1`, delivered as three ordered work-streams (each its own
implementation plan).

## Goal

Turn the hand-copied single-file script into an **installable, self-updating,
modular OVMS plugin** whose TLS "just works." No new telemetry features — pure
delivery, structure, and robustness, so it is cleanly testable against the
existing behavior.

## Scope

**In:** module split + a build/bundler; OVMS plugin packaging (manifest +
GitHub-Pages repo + `plugin install`/`update`); retire the manual hand-copy path;
cert handling (proactive curated-root install + reactive fallback).

**Out (other sub-projects / deferred):** `planning.js` and notifications (SP2);
web UI (SP3); OAuth2; auto-limit charging.

## Work-streams (ordered)

| # | Work-stream | Milestone | Behavior change? |
| --- | --- | --- | --- |
| WS1 | Module split + bundler | 3.0.0-alpha.1a | **No** (pure refactor) |
| WS2 | Plugin packaging + GitHub Pages distribution | 3.0.0-alpha.1b | No (delivery only) |
| WS3 | Cert handling (proactive curated-root install + reactive fallback) | 3.0.0-alpha.1c | Yes (new robustness feature) |

Order rationale: establish the modular structure + build first (under the existing
test suite, no behavior change), then package the bundled artifact, then add cert
handling into the new structure. WS3 is independent of WS1/WS2 and could move
earlier, but slots cleanly into `certs.js`/`iternio.js` last.

## WS1 — Module split + bundler

### Modules (`lib/abrp/*.js`)

Split today's `abrp.js` (~870 lines) into focused modules. `planning.js` is **not**
part of SP1 (SP2). Each module owns its state and exposes accessors (extends the
existing `__test` seam pattern); no god-`state.js`.

| Module | Responsibility |
| --- | --- |
| `util.js` | `logger`, `timestamp`, `clone`, `round`, `medianPowerMetrics` |
| `config.js` | token state, `validateUsrAbrpConfig`, reset |
| `metrics.js` | `metricMap`, `overrideMetricMap`, `isOvmsMetricSupported`, `getOVMSMetric`, `createTelemetry` |
| `queue.js` | queue/collected/lastQueued state, `queueTelemetry*`, `removeTelemetry`/`removeTelemetryBatch`, `isSignificantTelemetryChange`, `calculateMaxElapsedDuration` |
| `iternio.js` | shared transport: URL/key/token, `HTTP.Request` wrapper, `isApiOk`, optional reactive cert-heal-on-fail hook (WS3) |
| `telemetry.js` | `sendTelemetry`, `createBulkPost`, `sendBulkTelemetry`, `isSending` |
| `certs.js` | bundled non-embedded root PEMs (GoDaddy G2 + GlobalSign R1) + `ensureInstalled()` (proactive, idempotent) (WS3) |
| `events.js` | `subscribe`/`unsubscribe` + subscriptions state, vehicle callbacks, `manageVehicleStateEvents`, `checkTime`, `send` start/stop, `isActive`/`isTimeValid` |
| `abrp.js` *(entry)* | public commands (`info`, `onetime`, `send`, `resetConfig`), startup wiring, `module.exports` |

- **Inter-module requires use native relative ids** (`require('./queue')`), resolved
  at **build time** by the bundler — so the delivered file has no `require`s, and
  OVMS's no-relative-require / `plugin/` prefix limitations never apply.
- Modules are CommonJS (`module.exports`), matching Duktape.

### Bundler (`build.js`, dependency-free)

- A ~60-line Node script: reads the `lib/abrp/*` modules, wraps each in a minimal
  CommonJS shim (a tiny `require`/`module.exports` registry resolved in dependency
  order from the entry), and emits a single **Duktape-safe** `dist/abrp.js`.
- **Output guardrail:** the build runs a post-bundle assertion that the emitted file
  contains no `=>`, template literals, or object spread in code (the same check
  used on `lib/abrp.js` today). Source modules keep the ES2015 / `var`+`function`
  style.
- **Rejected alternative:** esbuild/rollup — their CJS interop helpers emit arrow
  functions / modern syntax even at `--target=es2015`, which the Duktape guardrail
  forbids and whose support on the target Duktape we can't guarantee. The custom
  concatenator gives full control of emitted syntax with zero toolchain risk.

### Testing

- Jest tests each module in isolation using **native relative `require`** (no
  `moduleNameMapper`). The existing 26 tests migrate to the relevant module specs.
- A **bundle smoke test**: build `dist/abrp.js`, `require` it under Jest with the
  host-global stubs, and assert the public surface (`info`/`onetime`/`send`/
  `resetConfig` + `__test`) behaves identically — proving the bundle equals the sum
  of its modules.

### Acceptance (WS1)

No behavior change: the bundled `dist/abrp.js` passes the full suite and the smoke
test; ESLint clean; output Duktape-safe. The single-file `lib/abrp.js` is replaced
by `lib/abrp/*` + `dist/abrp.js`.

### Follow-up: cap the `collectedMetrics` smoothing buffer (queue.js)

*Observed during 2.3.0 on-vehicle validation (drive of 2026-06-02): the
`collectedMetrics` median-smoothing buffer climbed to **160 samples** (~2.7 min of
1-second collection) before `Processing collected metrics` flushed it.* Today the
buffer is bounded only **indirectly** — by `calculateMaxElapsedDuration` forcing a
flush — and has **no independent `MAX_*` cap** like the telemetry send-queue's
`MAX_TELEMETRY_QUEUE_SIZE`. On the observed drive this self-limited fine, but a
future cadence change (or a long, uninterrupted steady-state cruise with no
significant change) could let it grow unbounded, holding many metric snapshots in
RAM and coarsening the median.

When `queue.js` is extracted in WS1, add a defensive cap on the `collectedMetrics`
buffer (cap size + drop-oldest, mirroring the send-queue overflow handling) so the
smoothing buffer is bounded independently of the cadence logic. Pure hardening — no
behavior change on normal drives. (This is a no-behavior-change refactor item, so it
fits WS1's "no behavior change" gate as long as the cap is set above the observed
steady-state peak.)

## WS2 — Plugin packaging + GitHub Pages distribution

### Manifest (`abrp.json`)

- One `module` element → the bundled `abrp.js` (so a single global `abrp`;
  `script eval abrp.info()` keeps working).
- `name: abrp`, `version` tracks the plugin `VERSION`, `maintainer`, `description`,
  `group`, `prerequisites: ["ovms>=3.3.004"]`.

### Distribution (GitHub Pages)

- A Pages site (served from this repo) hosts:
  - `plugins.json` (repo index, lists `abrp`)
  - `abrp/abrp.js` (bundled deliverable)
  - `abrp/abrp.json` (manifest / `EL_JSON` element)
- The **build publishes** these into the Pages directory, so a release is
  "rebuild + push."
- **TLS:** GitHub Pages chains Let's Encrypt → **ISRG Root X1**, which OVMS embeds
  in firmware — so `plugin install` from GitHub is trusted out of the box (no cert
  setup, no dependency on WS3).
- The exact Pages URL/org (`<org>.github.io/ovms-link`) is settled at
  implementation; an `openvehicles` default-repo submission is a later option.

### Install/update flow

- `plugin repo install abrp https://<pages-url>/` → `plugin install abrp` →
  `plugin update`. The plugin auto-loads (`require("plugin/abrp/abrp")`); **no
  `ovmsmain.js`** is shipped or edited.
- README rewritten: replace the hand-copy section with the plugin flow; keep the
  token-config step (config-page UI is SP3).

### Acceptance (WS2)

`plugin install abrp` from the Pages repo installs and runs the bundled plugin on a
real module; `plugin update` upgrades it; the manual-copy instructions are retired.

## WS3 — Cert handling: proactive curated-root install (+ reactive fallback)

`api.iternio.com` sits behind **Amazon CloudFront**, which **rotates the served
certificate chain over time** — verified by inspecting the live chain
(`iternio.com → Amazon RSA 2048 M01 → Amazon Root CA 1 → Starfield Services G2`),
and historically GoDaddy-rooted (the 2.x README's `gdroot-g2` requirement). That
rotation is the root cause of the intermittent "SSL Error" reports (#39, #35): the
module validates the chain when it roots in a firmware-embedded CA and fails when it
doesn't.

The module **cannot inspect the presented chain from JS** — a TLS failure surfaces
only an error string, not the certificates — so it can't identify the missing root
at runtime. Therefore the **primary** fix is **proactive**: install up front the
small, known set of CloudFront roots OVMS lacks, so any rotation is already trusted.

### Bundled certs (`certs.js`)

The needed set is the CloudFront-relevant roots **not** already in firmware
(`amazon_root_ca1`, `isrg_x1`, `digicert_global`, `digicert_g2`,
`baltimore_cybertrust`, `starfield_class2`, `usertrust`). Cross-referenced against
the committed `trustedca/` certs (identified by subject):

| `trustedca/` file | Root | In firmware? | Bundle? |
| --- | --- | --- | --- |
| `gdroot-g2.crt` | **GoDaddy Root CA – G2** | no | **yes** |
| `root-r1.crt` | **GlobalSign Root CA – R1** | no | **yes** |
| `isrgrootx1.pem` | ISRG Root X1 | yes | no |
| `amazon.pem` | Amazon RSA 2048 M01 (*intermediate*; its root is embedded) | n/a | no |

So `certs.js` embeds **two PEM constants — GoDaddy Root G2 + GlobalSign Root R1** —
taken verbatim from the committed `trustedca/` files (originally from the CAs'
public repositories). Pinned in-source; never fetched at build or runtime.

### Primary: proactive install (idempotent, at startup)

At init (inside the OVMS-only guard, **before sends begin**),
`certs.ensureInstalled()`:
1. For each bundled root, check whether it is already present in `/store/trustedca/`
   (e.g. `VFS.Load` the target path). If all present → **do nothing**.
2. Otherwise `VFS.Save` the missing PEM(s) to `/store/trustedca/abrp-<name>.crt`,
   then `OvmsCommand.Exec("tls trust reload")` **once**.

Idempotent: it writes/reloads only when a bundled cert is missing, so normal boots
don't touch the trust store. **No TLS-error classification, no guessing which root,
no false-positive risk** — this is the simplification over the earlier reactive
design.

### Fallback: reactive heal (secondary, optional)

If a send still fails with a TLS/X509 error (a future CloudFront root outside the
curated set), `iternio.js`'s `fail` handler may re-run `certs.ensureInstalled()`
**once per session** as a backstop. The 2.3.x at-least-once queue means the next
`ticker.10` retries for free. This path is a safety net only — the proactive install
covers the known cases — and **may be deferred** if proactive proves sufficient in
testing.

### Safety

Certs are **bundled/pinned** in the plugin and **never fetched over the network**
(fixing trust via an untrusted connection would be chicken-and-egg). The install
only ever **adds** the curated roots; it never removes or alters existing trust.

### Testing

With stubbed `VFS`/`OvmsCommand`:
- First run (certs absent) → `ensureInstalled()` writes the two PEMs + exactly one
  `tls trust reload`.
- Subsequent run (certs present) → **no** write, **no** reload (idempotent).
- (Fallback) a TLS-class `fail` triggers `ensureInstalled()` at most once/session;
  a plain network error does not.

### Acceptance (WS3)

On a fresh install, the two curated roots are present in `/store/trustedca/` after
first run, so a CloudFront chain rooting in GoDaddy/GlobalSign validates with **no
manual `tls trust` steps** — and a normal reboot performs **no** redundant
trust-store writes.

## Risks

- **Bundler correctness/Duktape-safety** — mitigated by the post-bundle syntax
  assertion + the bundle smoke test proving behavioral equivalence.
- **Migration** — plugin-only retires manual install; clear release notes; the
  GitHub-Pages repo + `openvehicles` redirect ease discovery.
- **CDN root outside the curated set** — if CloudFront ever serves a chain rooting in
  a CA that's neither firmware-embedded nor in our two bundled roots, the proactive
  install won't cover it; the reactive fallback (re-install + reload, once/session)
  is the backstop, and the curated set can be extended.
- **WS1 is a large refactor** — gated by "no behavior change" + the full existing
  suite; do WS1 fully before WS2/WS3.
